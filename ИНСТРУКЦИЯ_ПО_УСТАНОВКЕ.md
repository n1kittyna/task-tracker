# Task Tracker — обновление учебного проекта

Основание: исходный код публичного репозитория `https://github.com/n1kittyna/task-tracker`, ветка `main`, просмотрен 12 ноября 2026 года. Архив содержит **только новые/изменённые файлы**, а не полный GitHub-репозиторий.

## Как установить

1. Сохраните копию существующего репозитория (или создайте отдельную ветку Git):
   ```bash
   git switch -c practice-improvements
   ```
2. Распакуйте архив **в корневую папку** локального клона `task-tracker`. При запросе замените файлы из папок `app/` и `tests/` соответствующими файлами архива. Остальные файлы проекта оставьте без изменений.
3. Установите зависимости из уже существующего в репозитории `requirements-dev.txt`:
   ```bash
   python -m pip install -r requirements-dev.txt
   ```
4. Запустите тесты и посмотрите покрытие:
   ```bash
   python -m pytest -v
   python -m pytest --cov=app --cov-report=term-missing
   ```
5. После успешной проверки запустите проект обычным способом из исходного README:
   ```bash
   python manage.py run --debug
   ```
6. Изучите изменения и отправьте их в свой GitHub:
   ```bash
   git status
   git add app tests
   git commit -m "Improve task CRUD, filtering, access and tests"
   git push -u origin practice-improvements
   ```
   Или создайте pull request с этой ветки в `main`.

**Важно:** команды `init-db` и создание администратора нужны лишь для новой базы данных. Существующую БД не удаляйте: структура таблиц **не менялась**, миграции не требуются.

## Особенности и границы реализации

- **Миграция БД не требуется:** личная задача определяется сочетанием `created_by_id == assignee_id == id пользователя`. Это учебный компромисс, а не отдельная сущность/флаг.
- **Обычный сотрудник** не может назначать задачи другим людям. При создании и редактировании исполнитель **принудительно задаётся на сервере** как текущий пользователь. Изменение HTML-поля или POST-параметра не позволяет обойти правило.
- **Поиск кириллицы** использует Python `str.casefold()` над названием и описанием **задач в доступной пользователю области**, уже отфильтрованных через SQL по другим полям. Для небольших команд это простой переносимый вариант. Для десятков тысяч задач потребуется отдельный поисковый индекс или полнотекстовый поиск.
- **Сортировка** выполняется непосредственно в запросе SQLAlchemy **до пагинации**. При сортировке по сроку задачи без срока находятся в конце.
- Параметры фильтров и сортировки остаются в адресной строке, включая ссылки на следующую страницу.
- **Существующие маршруты и поля таблиц сохранены**, поэтому другие части кода должны работать без переписывания.

## Что проверить вручную после установки

1. Войти под сотрудником, нажать «+ Задача», создать, отредактировать и удалить свою задачу.
2. Убедиться, что задача, назначенная сотруднику менеджером, доступна для смены статуса, но не для изменения других полей и удаления.
3. В списке применить поиск по описанию и по слову в разных регистрах кириллицы.
4. Проверить четыре варианта сортировки и переход на вторую страницу с активными фильтрами.
5. Под администратором попробовать создать/отредактировать пользователя с чужим e-mail: должна появиться ошибка формы, а не ошибка сервера.
6. Отключить пользователя после его входа и убедиться, что следующая защищённая страница перенаправляет его на вход.
7. Проверить, что процент завершённых задач совпадает с данными по статусам.
